---
title: 在 Orca 中提交与推送
---

你可以在不离开 Orca 的情况下提交、推送并打开审阅。提交面板紧邻 Diff 查看器，专为常见场景设计 — 审阅、暂存、提交、推送，继续前进。

## 提交

1. 从源代码控制面板暂存已更改的文件。
2. 在底部面板编写提交信息，或使用 **用 AI 生成** 让 Orca 根据已暂存的变更起草一条。
3. 当焦点在源代码控制面板上且主要操作是提交时，按 **提交**（macOS 上 `Cmd-Enter`，Windows / Linux 上 `Ctrl-Enter`）。

仓库中的 pre-commit hooks 会照常运行。如果 hook 失败，Orca 会在内联中显示输出。

当提交失败时，使用失败详情中的 **用 AI 修复** 在活跃工作树中启动默认代理，传入 hook 输出、尝试过的提交信息和已暂存文件列表。代理只会收到一个修复提示 — 它不会被要求绕过 hooks、提交、推送或打开审阅。

## 推送

**推送** 会将工作树的分支推送到 `origin`，第一次会设置上游。如果分支落后，Orca 不会静默强制推送。

当你重写了历史（rebase、amend、squash），而远程只有本地提交的较旧副本时，源代码控制面板会将 **带 lease 的强制推送** 作为明确的单独操作展示 — 永远不会作为普通推送的备选。标签会显示正在替换的提交数量和上游分支名，让你知道确切要改变什么。强制推送使用 `--force-with-lease`，因此过期的远程本地视图会中止推送，而不是覆盖他人的提交。

## 打开托管审阅

分支推送后，使用源代码控制面板的托管审阅操作创建 pull request 或 merge request。提交前确认基础分支、标题、描述和草稿状态。Bitbucket Cloud 可以从同一个编辑器创建 pull request；它没有草稿 PR，因此 Draft 选项会隐藏。对于 GitHub，当选定的基础分支已有打开的 PR 时，你可以 **将此 PR 堆叠在 #N 之上** — 参见 [堆叠 pull request](/docs/review/github#stacked-pull-requests)。

如果 Orca 需要在创建 PR 流程中运行后续提交，而该提交失败了 — hooks 拒绝了它，或工作树处于不可提交的状态 — 对话框会显示包含 hook 输出和下一步按钮的详细失败摘要，而不是让你回到面板中没有上下文。从摘要中使用 **用 AI 修复** 将失败交给代理，或自己解决后重试。

在创建审阅对话框中使用 **用 AI 生成 pull request 详情**，让 Orca 根据分支 diff 和提交起草标题、描述和草稿状态。生成的文案针对简短的 ELI5 问题/解决方案章节和关联 issue 引导（当附加了 GitHub issue 时，区分 `Fixes` 与 `Refs`）。Orca 会保留你选定的基础分支，拒绝空描述，并显示清晰的错误让你可以重试，而不是发布空白正文。创建审阅前请先检查字段。

## 按仓库 AI 操作配方

**用 AI 生成**、**用 AI 生成 pull request 详情**、**用 AI 修复** 和 **用 AI 解决** 都是源代码控制 AI 操作 — 每个都由一个**操作配方** 支撑，它选择代理、CLI 参数和 Orca 运行该操作时使用的提示模板。在 [设置 → Git & 源代码控制](/docs/settings) → **操作配方** 下编辑它们，可以作为你的全局默认值，也可以限定作用于当前仓库。

模板可以包含诸如 `{basePrompt}`、`{branch}`、`{stagedFiles}`、`{stagedPatch}` 以及提交消息专用的 **`{linkedIssue}`** 之类的变量；PR 详情还支持 `{baseBranch}`、`{currentTitle}`、`{currentBody}`、`{commitSummary}`、`{changedFiles}` 和 `{patch}`。

`{linkedIssue}` 会展开为工作空间关联的 **GitHub issue 编号**，如果没有关联则为空（包括纯 Linear/GitLab 工作空间）。请优先使用引导式措辞 — 裸 `Fixes #{linkedIssue}` 在未关联时会变成 `Fixes #`。

当仓库对某个操作有自己的配方时，保存对全局默认值的更改不会影响它 — 设置面板会显示一个 **仓库覆盖** 注释，列出哪些仓库有分歧以及覆盖了什么（代理、CLI 参数或命令模板），并带有一个 **查看** 链接跳转到该仓库的设置，让你可以更新或移除覆盖。

## Amend

Amend 是显式操作 — **提交 → Amend**。Orca 不会对已推送的提交执行 amend，除非你确认。

## 源代码控制面板

侧边栏的 **源代码控制** 面板在不离开当前视图的情况下暴露同样的操作：暂存和丢弃文件、编写提交信息，以及作为一键操作运行 **提交**、**推送**、**拉取** 或 **同步**。路径渲染为 UTF-8，即使它们包含非 ASCII 字符。

顶部的分支上下文行显示当前分支（或 detached HEAD）堆叠在对比基础（`branch → base`）之上，这样创建 PR 和远程操作永远不会让你忘记当前所在的分支。当分支有可用的合并基础时，一个紧凑的标签会显示相对于该分叉点的增减总行数（一个范围 diff，不是暂存/未暂存区域的总和）。悬停标签可查看 **代码明细**（当主机发布拆分时）：**源码**、**测试** 和 **生成的**（仅当非零时才显示生成的）— 仅基于路径启发式，不是内容分析。长分支名会被截断，以免覆盖标签。

**在分支上提交** 显示的是相对于选定基础的共同祖先之后的变更。仅在基础分支上做的变更会被排除。如果未跟踪文件与该祖先删除或重命名的文件重叠，行数标签会清除之前显示的数字，直到确切总数再次可用。暂存该文件即可恢复确切总数。

右键点击已更改的文件可选择 **复制路径** / **复制相对路径**（相对于工作树根目录）。

面板底部的主要按钮会随状态变化，因此下一个有用的操作始终只需一键：有未暂存变更时是 **暂存文件**，然后是 **提交**，然后根据分支相对于其上游的位置显示 **推送** / **拉取** / **同步**。

当合并、rebase、cherry-pick 或 revert 留下冲突时，源代码控制面板会在 **审阅冲突** 旁显示 **用 AI 解决**，这样你可以选择将冲突集交给代理，或自己检查后再继续。对于不再想要的进行中的合并或 rebase，从源代码控制面板使用 **中止合并** 或 **中止 rebase**。
